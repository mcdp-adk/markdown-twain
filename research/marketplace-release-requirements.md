# Marketplace release requirements

Research date: 2026-09-28. Scope: [Research authentication and publication requirements for both extension registries](https://github.com/mcdp-adk/markdown-twain/issues/65), for a regular `0.x` GitHub Release using one VSIX for Visual Studio Marketplace and public Open VSX. No accounts were configured and nothing was published.

## Authentication findings and recommendation

Prefer short-lived or federated credentials for continuing automated releases when both the registry and the selected CLI support them. Direct GitHub OIDC is a candidate, not yet a verified runnable configuration for this repository.

The upstream `@vscode/vsce` [README](https://github.com/microsoft/vscode-vsce#trusted-publishing) documents `vsce publish --oidc`, a Marketplace trusted-publishing policy keyed to repository/workflow, and `id-token: write`. It says token acquisition or exchange failure does not fall back to a PAT. However, local read-only verification returned `4.0.0` for `pnpm exec vsce --version`, and `pnpm exec vsce publish --help` listed PAT and `--azure-credential` but **no `--oidc` option**. Upstream documentation therefore does not establish support in the project's installed package. Selecting a CLI artifact with verified flag support, and confirming the owner's private Marketplace policy controls, are prerequisites to choosing that path. No publish command was executed.

Open VSX's [CLI documentation](https://github.com/eclipse-openvsx/openvsx/blob/main/cli/README.md#trusted-publishing) and [trusted-publishing wiki](https://github.com/eclipse-openvsx/openvsx/wiki/Trusted-Publishing) describe `ovsx publish <file> --trusted-publishing` with `id-token: write`, after the namespace owner registers a workflow. Its first extension version must already be active, so the initial upload uses an access token.

The [public service repository's production configuration at commit `2f864cf`](https://github.com/EclipseFdn/open-vsx.org/blob/2f864cfd512e419ca9dc70608a657ca5bd452dc9/configuration/application-production.yml) sets `trusted-publishing.enabled: true`, audience `https://open-vsx.org`, and provider `github`. **This is configuration evidence, not a live deployment verification.** The file's own header says its values need confirmation against production infrastructure before merging. The upstream feature is [off by default](https://github.com/eclipse-openvsx/openvsx/wiki/Trusted-Publishing#for-registry-operators). Confirm availability in the signed-in public service, namespace eligibility, and support in the selected released `ovsx` package before relying on it.

The smallest sustainable choice remains conditional: use registry-native GitHub OIDC if the above checks pass; otherwise assess the documented Marketplace Entra flow and the available Open VSX token path against the owner's accounts. Do not make global Azure DevOps PATs the long-term dependency. Concrete credential placement and workflow/recovery policy remain downstream decisions.

## Other supported authentication paths

- Marketplace PAT: `vsce` accepts `--pat`/`VSCE_PAT`. Microsoft's recipe calls for Marketplace **Manage** scope and **All accessible organizations**. Microsoft states that **global** Azure DevOps PATs stop working on **2026-12-01**; its revised notice says creation remains allowed until that date. This is not a stated retirement date for every organization-scoped PAT. Avoid a global PAT as steady-state CI authentication. [VS Code guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#get-a-personal-access-token), [Microsoft retirement notice](https://devblogs.microsoft.com/devops/retirement-of-global-personal-access-tokens-in-azure-devops/), [vsce CLI source](https://github.com/microsoft/vscode-vsce/blob/main/src/main.ts).
- Marketplace Entra ID: Microsoft's documented workload-federated option sets up an Azure DevOps service connection and user-assigned managed identity, adds that identity as publisher **Contributor**, then uses `vsce publish --azure-credential`. The worked example targets Azure Pipelines, so it is not a direct GitHub Actions recipe. It remains an alternative if Marketplace OIDC policy is unavailable. [VS Code guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#secure-automated-publishing-to-visual-studio-marketplace).
- Open VSX PAT: `ovsx` accepts `--pat`/`OVSX_PAT`; the public guide recommends one token per publishing environment. It is needed for namespace setup and the first version before OIDC registration. [Public guide](https://github.com/EclipseFdn/open-vsx.org/wiki/Publishing-Extensions), [CLI](https://github.com/eclipse-openvsx/openvsx/blob/main/cli/README.md).
- Open VSX OIDC: `--trusted-publishing` fails if the job cannot obtain an ID token. A leftover `OVSX_PAT` takes precedence, so remove it from an OIDC job. Registration is not tied to a branch or tag; an optional pinned environment narrows use. [Trusted Publishing](https://github.com/eclipse-openvsx/openvsx/wiki/Trusted-Publishing), [CLI](https://github.com/eclipse-openvsx/openvsx/blob/main/cli/README.md#trusted-publishing).

## Manifest, package, and listing

The checked-out [`package.json`](../package.json) has `name: markdown-twain`, `publisher: mcdp-adk`, SemVer `0.0.1`, `engines.vscode: ^1.96.0`, `main: ./dist/extension.js`, description, repository, `license: GPL-3.0-or-later`, `private: true`, `vscode:prepublish: pnpm build`, and `package: vsce package --no-dependencies`. [`LICENSE`](../LICENSE) and [`README.md`](../README.md) exist. No manifest icon or `CHANGELOG.md` was found. These are local observations, not an accepted-registry validation.

The [VS Code manifest reference](https://code.visualstudio.com/api/references/extension-manifest) marks `name`, SemVer `version`, `publisher`, and `engines.vscode` as required; this manifest supplies them. It marks license, description, icon, and other listing fields optional. Where a root LICENSE exists, it says the license field **should** say `SEE LICENSE IN <filename>`; this documentation wording alone does not establish that the current SPDX value blocks publication. The [Marketplace guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#marketplace-integration) recommends README, LICENSE, changelog, support page, banner, and PNG icon as presentation additions. A supplied icon cannot be SVG, and README/CHANGELOG images must use HTTPS and avoid untrusted SVG. [Publishing constraints](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#publishing-extensions).

Build and package the bundled pnpm extension once with the repository's `--no-dependencies` path; inspect the VSIX contents and validate installation in desktop VS Code and VSCodium. Upload that same VSIX with `vsce publish --packagePath <file>` and `ovsx publish <file>`. The Open VSX CLI explicitly accepts an existing VSIX; `vsce`'s guide and source support `--packagePath`. `@vscode/vsce` 4.x requires Node 22 or later. [Open VSX CLI](https://github.com/eclipse-openvsx/openvsx/blob/main/cli/README.md#publish-extensions), [VS Code guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#platform-specific-extensions), [vsce README](https://github.com/microsoft/vscode-vsce#requirements).

Open VSX can reject publication after security scanning, including secret, blocklist, and namespace-similarity checks. `ovsx` checks the registry's package-size limit before upload. [Public publishing guide](https://github.com/EclipseFdn/open-vsx.org/wiki/Publishing-Extensions), [CLI](https://github.com/eclipse-openvsx/openvsx/blob/main/cli/README.md#publish-extensions).

## Success, duplicates, and one-sided success

Require a successful CLI exit for each upload and verify the matching ID/version in each registry's listing or metadata. Open VSX explicitly asks publishers to inspect the resulting metadata. Marketplace malware scanning may delay public availability, so upload acceptance and visibility are separate observations. [Open VSX result guidance](https://github.com/EclipseFdn/open-vsx.org/wiki/Publishing-Extensions#see-the-result), [VS Code security docs](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security#marketplace-protections).

`vsce` [checks version and target platform](https://github.com/microsoft/vscode-vsce/blob/main/src/publish.ts) before upload and errors on a duplicate unless `--skip-duplicate` is set; it treats a 409 race similarly. Open VSX [v1.1.0 release notes](https://github.com/eclipse-openvsx/openvsx/releases/tag/v1.1.0) describe immutable versions and fail-fast duplicate checks. Its [CLI docs](https://github.com/eclipse-openvsx/openvsx/blob/main/cli/README.md#delete-extensions) say deleted versions remain reserved. Do not rely on overwriting or deleting/reusing a version.

The registries have no shared transaction. If one succeeds, retain the exact VSIX and observed registry states, resolve the other registry's failure, and retry only the missing publication. Rebuilding or bumping just the second upload would violate the same-artifact requirement. The exact retry/skip and release-status policy belongs to the downstream workflow decision, not this research finding.

## Follow-up decisions and first-release prerequisites

1. Before implementation, verify which released CLI artifacts actually expose the documented OIDC options. The installed `vsce 4.0.0` observation must be resolved rather than assuming an upstream README describes that local artifact.
2. Owner access check: confirm control of `mcdp-adk` on both services, existing extension versions, the Open VSX agreement and namespace owner/member state, Marketplace trusted-publishing policy availability, and the public Open VSX trusted-publisher controls. This check does not upload a version.
3. Workflow decision: account for Open VSX's initial token-authenticated upload before its trusted-publisher registration can be established. That upload can occur in the first authorized GitHub Release workflow after validating the VSIX; the requirement does not inherently force a manual publication or publication before implementation. Enable trusted publishing only after an active version and the owner's registration exist. [Open VSX prerequisites](https://github.com/eclipse-openvsx/openvsx/wiki/Trusted-Publishing#before-you-start).
4. Settle the concrete initial version, release/tag/manifest alignment, workflow filename/environment, package and editor checks, and partial-success recovery policy after the account and tool facts are known. The non-prerelease GitHub Release trigger, dual-market scope, and desktop VS Code/VSCodium validation targets are already settled.
