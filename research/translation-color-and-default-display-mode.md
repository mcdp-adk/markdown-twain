# Translation color configurability and a default display mode

Research for [#90](https://github.com/mcdp-adk/markdown-twain/issues/90) ("Allow customizing the translation text color") and [#91](https://github.com/mcdp-adk/markdown-twain/issues/91) ("Option to keep the display mode across windows").

**Questions.** (1) Can users restyle `.twain-t` today with `markdown.styles`, and is the reporter's claim about it right? (2) Would a `contributes.colors` theme color reach the built-in Markdown preview as a CSS variable, and what rules govern its defaults and overrides? (3) What are the alternative color-config mechanisms and their costs, and how do established preview extensions do it? (4) What configuration `scope` fits an opt-in `markdownTwain.defaultDisplayMode`, and how do trust and sync treat it? (5) When does our extension activate relative to the first preview render, and what does an async mode switch plus `markdown.preview.refresh` right after activation do? (6) What do Read Frog and Immersive Translate do about default/remembered modes and translation colors? (7) Which repo constraints bear on both features?

## Verdict

1. **The #90 reporter's claim is wrong in the general case, right at the edges.** User `markdown.styles` stylesheets load *after* every contributed stylesheet (including our `media/preview.css`), so a same-specificity `.twain-t` rule in `markdown.styles` already wins today (§1). What is true: the file must live where the preview may load it from (workspace folder, or the document's own directory when no folder is open), remote `http(s)`/`file://` URLs also pass through, and in an untrusted workspace the setting is ignored entirely (the built-in lists it in `restrictedConfigurations`). So "can't override" is really "can't override *conveniently and always*".
2. **A contributed theme color is the evidence-favoured route for #90.** `contributes.colors` accepts an id plus `light`/`dark` hex defaults (each either `#RRGGBB[AA]`/`#RGB[A]` or a reference to another color id; `highContrast`/`highContrastLight` fall back to `dark`/`light`), and the webview theming code exports *every* registered color — including extension-contributed ones — as `--vscode-<id-with-dots-as-dashes>` CSS variables into all webviews, markdown preview included. Users override with `workbench.colorCustomizations`, including per-theme `"[Theme Name]"` blocks, and changes apply live to an open preview with no reload. The contribution point dates to VS Code 1.16, far below the repo's `^1.96.0` engine. Costs: the two `oklch()` greens must be converted to hex and their contrast re-verified; and `preview.css` currently has no `body.vscode-high-contrast-light` rule, which a theme-color design should fix at the same time (§2, §7).
3. **For #91, an application-scoped opt-in `markdownTwain.defaultDisplayMode` defaulting to `originalOnly` fits every constraint checked.** `application` scope means user-settings-only (preserving story 63's "a workspace can't redirect my key" guarantee and the README's "Connection settings live in User Settings"), it syncs across machines via Settings Sync, and it sidesteps Workspace Trust `restrictedConfigurations` (there are no workspace-defined values to gate). Activation timing is safe: our `activate()` is fully synchronous and the engine awaits each plugin before the first render, so a default read at startup applies before anything paints; the existing async `setDisplayMode` + `markdown.preview.refresh` path already handles the late case as a forced full re-render. The one real cost is semantic, not technical: story 7 ("every window starts in `originalOnly`") changes from an invariant into a default, and the first render under a non-`originalOnly` default sends document text without a per-window click — which is exactly what "opt-in" means, but the README and the v1 spec must say so (§4, §5, §7).
4. **Do not decide "remember last mode" by analogy with browsers alone.** Both Read Frog (persisted `mode`, default `bilingual`) and Immersive Translate (default bilingual, remembers the toggled mode, per-site/per-language auto-translate and mode-exception rules) lean towards remembering, but both *also* keep an explicit default and, crucially, gate *automatic sending* behind separate opt-in site/language lists — the equivalent of our per-window click. The reporter's explicit-default proposal matches the repo's story-7 lineage better than silent persistence (§6).

## 1. `markdown.styles` reality check

**How entries are resolved** ([mlf-renderer], [mlf-config], [mlf-resources]):

- `markdown.styles` is declared in [mlf-pkg] (~L1742–1750) as a string array, default `[]`, with `"scope": "resource"` — settable at user, workspace, *and* folder level. Its description ([mlf-nls], `markdown.styles.dec`) reads: *"A list of URLs or local paths to CSS style sheets to use from the Markdown preview. Relative paths are interpreted relative to the folder open in the Explorer. If there is no open folder, they are interpreted relative to the location of the Markdown file."*
- Each entry becomes `<link rel="stylesheet" class="code-user-style" …>` ([mlf-renderer] L198–207, `#computeCustomStyleSheetIncludes`). Resolution (`#fixHref`, L174–196): `http:`/`https:`/`file:` URLs pass through untouched (L179–181); absolute filesystem paths go through `vscode.Uri.file` (L184–186); otherwise workspace-relative if the document is in a workspace (L189–193), else relative to the Markdown file's own directory (L195).
- **Order: contributed styles first, user styles last.** `#getStyles` (L234–243) emits `contributions.previewStyles` (which includes the built-in `media/markdown.css` + `media/highlight.css` from [mlf-pkg] L1888–1891 *and* our `media/preview.css` via our own `markdown.previewStyles` contribution) and only then the user's stylesheets. Equal specificity therefore resolves in the user's favour. (This also matches the Markdown extension guide's statement that user styles load after contributed ones, cited in the prior research §1.)
- **Load gating:** local files must fall under the webview's `localResourceRoots`, which for the preview are the contributing extensions' install dirs plus the workspace folders (or the document's directory when there is no workspace folder) ([mlf-resources] L15–35; aggregation of extension roots in [mlf-ext] L120). The API docs confirm a webview can only load local resources from `localResourceRoots` (`WebviewOptions.localResourceRoots` reference). So a stylesheet in `/tmp`, another extension's folder, or a non-workspace location is blocked even if `#fixHref` rewrites it.
- **Trust gating:** the built-in declares `capabilities.untrustedWorkspaces: { supported: "limited", restrictedConfigurations: ["markdown.styles"] }` ([mlf-pkg] L38–45). In Restricted Mode the setting keeps only its default (`[]`), so no user stylesheet loads at all.
- **Refresh behaviour:** any configuration change makes the built-in call `previewManager.updateConfiguration()` ([mlf-shared] L79–81), which re-renders a preview only if its cached `MarkdownPreviewConfiguration` (which includes `styles`) actually changed ([mlf-preview] L839–843; [mlf-config] L66 for `this.styles`). Editing `markdown.styles` therefore re-renders open previews by itself — no manual refresh needed.

**Is the reporter right?** No, with two true cores. A user *today* can restyle `.twain-t` by adding a workspace-local CSS file to `markdown.styles` with either `.twain-t { … }` (same specificity, later stylesheet wins) or anything more specific. This is not theoretical: bierner's Markdown Preview Github Styling tells its users exactly this — *"Customize styling using your own `markdown.styles` css … Make sure you apply your styles to the `.github-markdown-body` instead of just `body` so they don't get overridden by this extension"* ([marketplace page](https://marketplace.visualstudio.com/items?itemName=bierner.markdown-preview-github-styles)). What the reporter gets right: (a) it only works for files the preview is allowed to load (workspace/doc-dir), and (b) it silently does nothing in untrusted workspaces — both plausibly matching their experience. There is also no discovery: nothing tells the user the class is called `.twain-t`.

## 2. Contributed theme colors in the Markdown preview

**They reach the preview.** `WebviewThemeDataProvider.getWebviewThemeData` ([webview-themeing] L54–99) builds the style map by reducing over `colorRegistry.getColorRegistry().getColors()` (L64–69) — the *whole* color registry, which is where `contributes.colors` registers extension colors (`colorRegistry.registerColor`, [color-extpt] L139–145). Each entry is exported as `'vscode-' + entry.id.replace('.', '-')`. A contributed `markdownTwain.translationForeground` would therefore be usable in `preview.css` as `var(--vscode-markdownTwain-translationForeground)` in every webview, and the Markdown preview is a webview. This matches the documented guarantees from both sides: the Theme Color reference says *"Theme colors are available as CSS variables in webviews"*, and the Webview guide shows `editor.foreground` becoming `var(--vscode-editor-foreground)`. (Verified in source, not just docs: the registry iteration has no built-in-only filter.)

**Allowed default formats** ([color-extpt]):

- `defaults.light` and `defaults.dark` are **required** (schema `required: ['light', 'dark']`, L82; validation errors otherwise, L126–129).
- Each value is either a hex color — `#RRGGBB[AA]`, and per the validation message also the short forms `#RGB[A]` (L102–111, `parseColorValue`: leading `#` → `Color.Format.CSS.parseHex`) — or **the identifier of another themable color** which supplies the default (descriptions L50, L58). There is no `null`: an empty string is rejected by the same validation. So "no opinion in this theme kind" is expressed by referencing an existing color id, not by omitting the key.
- `defaults.highContrast` / `defaults.highContrastLight` are optional and fall back to `dark` / `light` respectively (L65–74 descriptions; L143–144 `defaults.highContrast ?? defaults.dark`). A HC design that wants "no color, dashed underline" (today's `preview.css` behaviour) would set the HC default to a suitable system color id and keep the underline in CSS — or keep `color: inherit` while still contributing the color for the non-HC kinds.
- The public docs agree on formats: *"the following hexadecimal notations are supported: #RGB, #RGBA, #RRGGBB and #RRGGBBAA"* (Theme Color reference, "Color formats").

**User overrides** (all public docs, confirmed against source where stated):

- Users override any color — including extension-contributed ones, which *"appear when using code complete in the `workbench.colorCustomizations` settings"* (Theme Color reference, "Extension colors") — via `"workbench.colorCustomizations": { "<colorId>": "#…" }`.
- Per-theme blocks use `"[<Theme Name>]": { … }`, with multi-theme and wildcard forms (`"[Abyss][Red]"`, `"[Monokai*]"`) and `"default"` to reset one customization (Color Themes doc, "To make customizations to a specific theme…"). Same mechanism covers token colors; nothing in source scopes it to built-ins.
- **Live update without reload (verified in source).** Changing `workbench.colorCustomizations` hits `installConfigurationListener` ([wb-themesvc] L340–385): `setCustomColors` (L361–362), then `applyColorThemeOverlays` and `onColorThemeChange.fire` (L373–376). That resets the cached webview theme data ([webview-themeing] L38–39, L101–104) and every webview element re-sends its `styles` (CSS variables) on `onThemeDataChanged` ([webview-element] L312, L697–710) — the page is not rebuilt, the variables just change under the existing stylesheet. Since the translated HTML carries no inline colors in this design, an open preview repaints with zero extension involvement.

**Minimum version.** The `colors` contribution point dates to VS Code 1.16 ("extension authors [can] contribute new themable colors", [1.16 release notes](https://code.visualstudio.com/updates/v1_16)); CSS-variable theming of webviews and the `vscode-high-contrast-light` body class (see the `ApiThemeClassName` enum, [webview-themeing] L106–121) are likewise years older than the repo's `^1.96.0` engine. Nothing relied on here needs a version bump.

## 3. Alternatives for color config, and what other extensions do

**Option A — a `markdownTwain.*` color setting injected by the markdown-it plugin.** Two injection shapes, both with a working precedent:

- *Data attribute + existing stylesheet.* The Mermaid extension exposes `markdown-mermaid.lightModeTheme` / `darkModeTheme` enum settings (`package.json` at `master`, `contributes.configuration`), injects them into the rendered HTML as `data-dark-mode-theme` / `data-light-mode-theme` / `data-max-text-size` on a `<span>` (`src/vscode-extension/themeing.ts` → `injectMermaidTheme()`), and its preview script reads them (`src/markdownPreview/index.ts` at `f011fde`, theme picked by `vscode-dark`/`vscode-high-contrast` body classes). The pattern's own author describes it as: *"Preferences are injected into rendered Markdown page by markdown-it plugin, as configuration API is not directly accessible from the webview"* (mermaid PR #142). Our plugin already emits the `.twain-t` elements themselves (`src/core/twain.ts` L34–70), so it could equally emit a resolved color — no preview script needed.
- *Inline `<style>` or `style=` in the rendered HTML.* The preview CSP allows it: every security level includes `'unsafe-inline'` in `style-src` ([mlf-renderer] L265, L268, L275). Whether the pipeline preserves a plugin-emitted `<style>` element or `style` attribute end-to-end is **not verified from source** — the Mermaid precedent proves elements and `data-*` attributes survive, but nobody injects `<style>` — so this needs the runtime check in §8.

Costs of a setting either way: the value needs validation in core (free-form color strings must be rejected or sanitized somewhere — and per the "adapter holds no decisions" rule, `src/extension.ts` L1–3, that means core); a single string cannot express light/dark/HC variants without inventing a mini-format (multi-field settings or per-theme settings multiply the surface); and it does not refresh for free — the built-in's config-change path only re-renders when *its own* `MarkdownPreviewConfiguration` changed ([mlf-preview] L839–843), so the extension must call `markdown.preview.refresh` itself (as it already does on `settingsChanged`). Worse, our `onDidChangeConfiguration` handler aborts in-flight runs on *any* `markdownTwain.*` change (`src/extension.ts` L174–176 → `settingsChanged()` → `abortRun()`, `src/core/translation.ts` L521–527): tweaking a color mid-run would restart translation, unless the handler learns to distinguish cosmetic settings.

**Option B — a CSS custom property users could set.** There is no user-writable CSS injection point besides `markdown.styles` (§1): a `--twain-*` variable is only settable from stylesheets the preview loads, i.e. contributed ones or `markdown.styles` itself. So "expose `--twain-translation-color`" collapses to: our stylesheet declares the variable with a default, and a user overrides it from their own `markdown.styles` file. That is strictly more cumbersome than overriding `.twain-t` directly, and buys nothing on its own. It becomes useful only *combined* with Option A or the theme color: the plugin (or the theme registry) sets the variable, `preview.css` consumes it in one place.

**Option C — contributing extra `markdown.previewStyles`.** Static per installation: the extension could ship alternate stylesheets, but contributions cannot be toggled per user without enable/disable gymnastics, and ordering between contributors is merge order ([mlf-ext] L76–84). No established extension styles this way. Not recommended; listed for completeness.

**How bierner's Github-styling extension does it** (`mjbvz/vscode-github-markdown-preview-style`, `master`): ships **twelve** stylesheets through `markdown.previewStyles` (base + light/dark/colorblind/tritanopia/high-contrast variants) and exposes the *choice* as three enum settings — `markdown-preview-github-styles.colorTheme` (`auto`/`system`/light/dark single-theme) plus `lightTheme`/`darkTheme` pickers with nine GitHub themes each (`package.json`). I.e. preset stylesheets + enum setting, no freeform colors, no theme-color contribution. Notably its marketplace page still defers fine-grained user CSS to `markdown.styles` (quoted in §1) — evidence that `markdown.styles` overriding is the community-accepted escape hatch.

**Trade-off summary.** Theme color (§2): per-theme/light/dark/HC support, live update, user overrides incl. per-theme blocks, and zero new settings plumbing — at the cost of hex-only defaults (re-verify contrast) and one new public color id to document. Setting injection: full programmatic control (any format, validation, could even keep `oklch()`), but single-valued unless multiplied, aborts runs on change as the code stands, and re-invents what the theme system already does. `markdown.styles` alone: works today for the motivated (§1), but undiscoverable and gated by workspace/trust.

## 4. Configuration scopes for a default-display-mode setting

**Official semantics** ([contribution-points](https://code.visualstudio.com/api/references/contribution-points#contributes.configuration), "scope"):

- `application` — *"Settings that apply to all instances of VS Code and can only be configured in user settings."*
- `machine` — *"Machine specific settings that can be set only in user settings or only in remote settings … The value of these settings will not be synchronized."*
- `machine-overridable` — *"Machine specific settings that can be overridden by workspace or folder settings. The value of these settings will not be synchronized."*
- `window` — *"Windows (instance) specific settings which can be configured in user, workspace, or remote settings."* (The default when no scope is declared.)
- `resource` — *"Resource settings, which apply to files and folders, and can be configured in all settings levels, even folder settings."*
- `language-overridable` — *"Resource settings that can be overridable at a language level."*

So: **a workspace `.vscode/settings.json` cannot set an `application`-scoped setting** — `defaultDisplayMode` with `scope: application` would be user-settings-only by construction. (`window` or `resource` would permit a workspace value.) In source, scopes route settings into separate schema buckets (`applicationSettings`, `windowSettings`, …) in `ConfigurationRegistry.updateSchema` ([config-reg] L974–996). The exact ignore-workspace-values enforcement point was not traced to a line; the docs sentence above plus the Settings editor hiding such settings from workspace scope is the citable behaviour, with a runtime check in §8.

**Workspace Trust / Restricted Mode.** Trust gates *workspace-defined values* of listed settings: *"For the settings listed, the extension will not be given workspace-defined values when in Restricted Mode"* and *"VS Code will only return the user-defined value of the setting in Restricted Mode … When trust is granted, a configuration change event will fire"* ([workspace-trust guide](https://code.visualstudio.com/api/extension-guides/workspace-trust)). An application-scoped `defaultDisplayMode` has no workspace-defined values by definition, so it needs no `restrictedConfigurations` entry. Two adjacent facts matter, though. First, the built-in puts `markdown.styles` in `restrictedConfigurations` ([mlf-pkg] L38–45), so the §1 workaround is unavailable in untrusted workspaces. Second, our `package.json` declares **no** `capabilities` block at all, and the default when absent is *not supported*: `getExtensionUntrustedWorkspaceSupportType` returns `false` unless the manifest, product.json, or user settings say otherwise ([ext-manifest] L194–226). With `main` present, the extension is therefore currently disabled outright in Restricted Mode — trust posture today is all-or-nothing, and neither #90 nor #91 changes that as long as new settings stay application-scoped. (If the owner ever declares `supported: true`/`"limited"`, a workspace-visible default mode would deserve a fresh trust review: a malicious workspace couldn't choose *where* text goes — provider and key stay user-scoped — but it could choose *whether* text is sent.)

**Settings Sync.** Sync covers *"User settings, except settings with the `machine` or `machine-overridable` scope"* ([Settings Sync doc](https://code.visualstudio.com/docs/configure/settings-sync)). An application-scoped default mode roams across the user's machines like `targetLanguage` already does — arguably the desired behaviour for "keep my mode", worth one line in the docs.

**How this repo scopes today, and why.** All six existing settings (`targetLanguage`, `provider`, `customBaseUrl`, `customApiKeyEnv`, `model`, `reasoningEffort`) are `"scope": "application"` (`package.json`, `contributes.configuration.properties`), and connection writes go to `ConfigurationTarget.Global` (`src/extension.ts`, `updateSetting`). The reasons are on record: issue #21's acceptance criteria pin `"scope": "application"` for the Target language setting, and v1 story 63 demands *"connection settings to be User-level only, so that a workspace I open can't redirect my key to its own server"* ([#19](https://github.com/mcdp-adk/markdown-twain/issues/19)). The README states it as a promise: *"Connection settings live in User Settings, not workspace settings"* (`README.md` L52). A `defaultDisplayMode` setting scoped `application` extends this lineage; scoping it `window`/`resource` would break it (a workspace could then opt the user into sending document text — precisely the story-63 shape).

## 5. Activation and first-render timing

**When our extension activates.** Our manifest has `"activationEvents": []` (`package.json`), so nothing activates us directly. Activation comes through the built-in: mlf itself activates on `onLanguage:markdown`, `onWebviewPanel:markdown.preview`, `onCommand:markdown.api.render`, and friends ([mlf-pkg] L27–38); when it collects contributions it calls `extension.activate()` for every contributor with `markdown.markdownItPlugins` and then `exports.extendMarkdownIt(md)` ([mlf-ext] L133–147, `getContributedMarkdownItPlugins`). Our `activate()` (`src/extension.ts` L31–201) is **fully synchronous** — it builds the core, registers commands, mirrors the display-mode context key (L198), and returns `{ extendMarkdownIt }` with no await in between.

**When `extendMarkdownIt` runs relative to the first render.** The shared engine builds its markdown-it instance lazily and `await`s each contributed plugin *before* the built-in's own renderers and before `pluginSourceMap` ([mlf-engine] L137–158, loop at L140–146). So the order in every window — including a window restoring an already-open preview on startup (restore re-creates the preview input, which triggers mlf activation and the lazy engine build) — is: our `activate()` → `extendMarkdownIt` wraps `md.renderer.render` → first render. A default mode read synchronously in `activate()` (today's `readSettings()` is a synchronous `getConfiguration`, `src/extension.ts` L204–216) therefore applies *before anything paints*: no flash of `originalOnly`, no extra refresh. This is the natural implementation shape for the proposed setting, and it needs no async machinery.

**The async late-switch path already exists and is safe.** `setDisplayMode` (`src/core/translation.ts` L499–520) awaits `preflight` (key/provider/model validation only — `check()` is `ready(true)`, which resolves the key and validates without any network call, `src/core/connection.ts` L113–125, L213–215), then sets `mode` and calls `deps.refresh()` → `markdown.preview.refresh`, a registered built-in command ([mlf-pkg] L193–194) that clears the engine cache and force-refreshes every preview (prior research §2). Overlapping switches are serialized by `modePickVersion` (L147, L500–505); a switch that lands mid-first-render just schedules one more forced full re-render, and renders inside the quiet period send nothing beyond the latest render's misses (v1 spec, Further Notes). Our render wrapper also reads `execution.displayMode` live on every render (`src/core/twain.ts` L34), so the re-render picks the new mode up without re-wrapping anything.

**Cases where a preview shows without our extension active.** (1) The WYSIWYG Markdown Editor (`vscode.markdown.preview.editor` is the *preview* custom editor, which is covered; the separate Markdown Editor does not consume `markdownItPlugins`/`previewScripts`/`previewStyles` — prior research §1). (2) Our extension disabled or uninstalled. (3) Our `activate()` throwing or returning no `extendMarkdownIt` — the built-in falls back to an identity plugin ([mlf-ext] L139–145). In all three, no translation markup is emitted and no setting is read; a `defaultDisplayMode` is simply inert. There is no case where the built-in renders a *preview* through the shared engine without giving contributors a chance to activate first — the plugin loop is on the render path itself.

## 6. Prior art: Read Frog and Immersive Translate

**Read Frog** (`mengxi-ream/read-frog` at `10c2684`, the project's stated inspiration — `README.md` Credits):

- Display mode is **persisted config with an explicit default**: `translate.mode: "bilingual"` (`src/utils/constants/config.ts` L52). The mode is toggled from UI/shortcut and the config object is the persisted (wxt-storage) config — i.e. *remember-last-mode with a bilingual default* (persistence mechanism inferred from the storage-backed `Config` and the live `storage.watch` propagation in `src/entrypoints/host.content/index.tsx`; the toggle-to-config write itself is listed as a runtime check in §8).
- **Auto-start is a separate opt-in axis.** `translate.page.autoTranslatePatterns` (default `["news.ycombinator.com"]`, L60) and `autoTranslateLanguages` (default `[]`, L61) decide *whether* translation starts by itself. The docs confirm: *"Auto Translate Websites … Never Auto Translate Websites … Auto Translate Languages … These lists are for automatic startup only"* ([Translation Settings](https://www.readfrog.app/en/docs/advanced-translation)). "Never" wins over "Auto" on conflicts. So Read Frog never conflates "which mode" with "whether to send": mode is remembered, sending is allow-listed per site/language.
- **Translation styling is preset + custom CSS.** `translationNodeStyle: { preset: TRANSLATION_NODE_STYLE_ON_INSTALLED, isCustom: false, customCSS: null }` (L83–86), where the on-install preset is `"textColor"` and the style vocabulary is `["default", "blur", "blockquote", "weakened", "dashedLine", "border", "textColor", "background"]` with a `read-frog-custom-translation-style` attribute for custom CSS (`src/utils/constants/translation-node-style.ts`). Our `preview.css` header notes it is "Read Frog's green" — the lineage is direct. Note the contrast with our world: a browser extension can ship arbitrary styling UI; we get the theme-color registry (§2) instead.

**Immersive Translate** (official docs):

- *"Immersive Translate defaults to bilingual display mode"* ([usage docs](https://immersivetranslate.com/en/docs/usage/)).
- It **remembers the toggled mode**: *"By default, the system will remember the mode toggled by clicking the icon in the panel for bilingual comparison or translation-only display. To switch temporarily, click 'More' -> 'Switch to translation-only display'"* (changelog 1.9.3). Plus per-language/per-website **mode exceptions** (changelog 1.9.1: default bilingual but Traditional Chinese → translation-only, configurable both ways), and zh↔traditional-chinese auto-selecting translation-only.
- I.e. the same two-axis shape as Read Frog: an explicit default mode, memory of the last choice, and scoped auto/exception rules — with auto-translate itself a per-site opt-in ("In-site auto translation", changelog).

**The norm, translated to our setting.** Neither tool has workspaces, so "scope" has no analogue; the transferable pattern is: *explicit default + remember-last + separate allow-list for automatic sending*. #91's proposal implements the first third. The second third (remember-last, e.g. in `globalState`) would go beyond the proposal and cut against v1 story 29's *"translations cached in memory for the session"* spirit and story 7's per-window opt-in — flag it as a deliberate scope decision, not an oversight. The third third (per-workspace/per-document auto rules) is what `window`/`resource` scope would enable, and §4 gives the reason not to.

## 7. Repo constraints on both features

- **Privacy promises (README + v1 spec).** *"Opening a preview in **Original Only** sends no document text to the provider; translation starts when you select a translated Display mode"* (`README.md` L3); *"The Display mode … starts as Original Only in each new window"* (L21); the send boundary is the 12,000-char Document brief plus untranslated Blocks (L35). V1 stories: 6 (one Display mode per window), 7 (*"every window to start in `originalOnly`, so that nothing is translated (or billed) until I ask for it"*), 47 (stay `originalOnly` when preflight fails), 63 (User-level-only connection settings), 22 (nothing sent mid-keystroke) — all in [#19](https://github.com/mcdp-adk/markdown-twain/issues/19). A non-`originalOnly` default keeps the letter of "opt-in" (the user sets it) but retires story 7 as an invariant; the README lines above and the spec must be reworded from guarantee to default. Technically the exposure is bounded: `preflight`/`check()` performs no network I/O (`src/core/connection.ts` L113–125), so the *only* new sending a default causes is the translation run itself.
- **Contrast requirements (#11).** The prototype chose variant B, "Theme-tuned pair: same hue, darker on light themes; HC: text colour + dashed underline" (`origin/prototype/translation-styling`, commit `2c6a90c`), and `media/preview.css` records `/* light: ≥5.1:1 */` and `/* Read Frog's green */` next to the two `oklch()` values, with HC as `color: inherit` + dashed underline. Any color mechanism must preserve all three: the ≥5.1:1 light contrast, the dark green, and the HC underline. Two concrete consequences: (a) hex-ifying the `oklch()` defaults for `contributes.colors` requires re-measuring contrast against the default light/dark editor backgrounds — the values may need adjusting, not just converting; (b) `preview.css` has **no `body.vscode-high-contrast-light` rule**, so HC-light themes currently fall through to the *light* teal — a latent gap a theme-color design (which has a first-class `highContrastLight` default) should close, after checking what body class the preview actually gets in HC light (§8).
- **"The adapter holds no decisions"** (`src/extension.ts` L1–3). New settings are read in `readSettings()` but interpreted in core: `Settings` flows into `createTranslation` and `settingsChanged()` already funnels every `markdownTwain.*` change to `abortRun()` + conditional refresh (`src/core/translation.ts` L521–527). A cosmetic-only color setting that aborts in-flight runs would violate the spirit of story 64 (never mix old and new) without buying correctness — the handler needs a cosmetic-vs-substance split, or the color must not live in `markdownTwain.*` at all (another point for `contributes.colors`, which bypasses the handler entirely).
- **Docs that must change.** `README.md` (the L3/L21/L52 promises), `GLOSSARY.md` if a new term lands (e.g. a named color id), the setting/color descriptions in `package.json`, and the v1-spec story 7 wording by reference. No new docs infrastructure is needed.
- **History for/against configurability.** Nothing closed decided *against* either feature. Direction is *for*: on 2026-10-15 the owner replied on #90 that *"I've already started working on configurable translation colors and an opt-in default display mode setting"* (reporter he-sirui stood down from a PR), and #91's reporter explicitly proposed `` `markdownTwain.defaultDisplayMode` (defaulting to `originalOnly`) `` with the opt-in rationale already internalized. This research informs that in-flight work; it does not re-decide it.
